# QA & Production-Readiness Audit — 3 August 2026

**Scope:** full-platform acceptance review against a live Kubernetes cluster.
**Method:** `kind` cluster `qa` (Kubernetes v1.36.1), namespace `payments`, nine
deliberately faulted workloads plus one healthy control. Backend run from source
in single-process mode, `AUTH_MODE=token`, three principals (owner / viewer /
foreign admin). Every claim below is backed by an observed response, a stored
artefact, or a line of code — nothing is inferred from the presence of a test.

---

## 1. Executive Summary

This is a well-architected platform. The seams are real, not aspirational: the
provider abstraction genuinely hides the transport, authorisation genuinely
fails closed, the evidence spine genuinely carries provenance, and the
deterministic fallback genuinely produces a complete diagnosis with no model
available. Against nine simultaneous real failures it collected 49 evidence
records at 93% completeness, derived 36 signals and 7 hypotheses, built a
19-node dependency graph, and named a correct root cause — in 0.2 s of platform
work. The healthy control workload was **not** flagged. That is a strong result
and most of this report is detail on top of a system that works.

The finding that matters is not any single bug. It is that **the test suite,
the linter and the eval corpus were all green while the platform failed to
diagnose an ImagePullBackOff sitting in front of it.** 1,172 tests pass, ruff
is clean, the golden corpus scores 13/13 and the grounding corpus 11/11 — and a
textbook Kubernetes failure, one of the two most common in production, produced
no dedicated signal, no hypothesis and no remediation plan. The cause is a
shape mismatch between what real `kubectl get pods -o json` returns and what the
test fakes feed in. Every fake supplies the aggregated, kubectl-display-style
status string; the real API server supplies a pod *phase* plus a separate
container *waiting reason*. The code reads the former. The tests can never
catch it because the tests are written against the same misunderstanding.

Two defects rise to HIGH. One suppresses a diagnosis that should fire
(**BUG-01**); one produces a confident, self-contradicting diagnosis that
should not (**BUG-02** — a missing ConfigMap reported as "Image or tag does not
exist in the registry"). A third HIGH (**BUG-05**) corrupts every non-ASCII
character in the PDF deliverable, which is the artefact most likely to reach a
customer's incident record.

None of these are architectural. All are localised, and all are fixable in the
low tens of lines. The architecture is not what needs work; the **fidelity of
the test inputs** is.

**Verdict: not yet ready for a Fortune 500 production deployment, but close.**
The blocking items are BUG-01, BUG-02 and BUG-05.

> **Status, same day: all Tier-1 items are fixed and verified against the same
> live cluster.** `ledger`'s ImagePullBackOff is now diagnosed with a dedicated
> 90% CRITICAL hypothesis that previously did not exist at all; the missing
> ConfigMap is no longer reported as a missing image; all three PDF fonts
> declare `/WinAnsiEncoding`; request fields are bounded. See

>

## 3. Bug Report

### BUG-01 — Pod phase shadows the container waiting reason (HIGH)

**Component:** `backend/app/kubernetes/pod_inspector.py:110`

`_detect_pod_status` tests the pod *phase* against `PROBLEM_STATUSES` and
returns it **before** examining `containerStatuses`:

```python
if phase in PROBLEM_STATUSES:      # "Pending" is in this set
    return phase                   # <- returns here
for container_status in status.get("containerStatuses", []):
    ...                            # <- ImagePullBackOff lives here, never reached
```

A pod failing to pull its image has `phase: Pending` **and**
`containerStatuses[0].state.waiting.reason: ImagePullBackOff`. `Pending` wins,
so the specific and actionable reason is discarded.

**Evidence (live, run `574f4e0c`):**

```
kubectl:   ledger-5474c5c9bf-gtp9c   phase=Pending   waiting=ImagePullBackOff
platform:  ledger-5474c5c9bf-gtp9c   ->  "Pending"

pod.image_pull_failure   -- NOT FIRED --
hypotheses: [workload.application_startup_failure, network.service_without_endpoints,
             storage.claim_blocking_pod, rollout.stalled, scheduling.unschedulable,
             storage.volume_unavailable, probe.failing]      # no image hypothesis
```

The control case proves the mechanism: `checkout` and `fraud-scorer` have
`phase: Running`, which is *not* in `PROBLEM_STATUSES`, so the loop **is**
reached and `pod.crash_loop` fires correctly for all three. The signal only
disappears when the phase happens to be a problem status itself.

**Impact.** `POD_IMAGE_PULL_FAILURE` is one of only two triggers for the
`image.pull_failure` hypothesis (`hypothesis_rules.py:118`); the other,
`EVENT_IMAGE_PULL_FAILURE`, requires an `ErrImagePull` event that has not yet
aged into `ImagePullBackOff`. Once a pod settles — which is the steady state an
operator actually investigates — **neither trigger fires**, so no hypothesis is
generated and `remediation/rules.py:366` never builds an image plan. The same
path swallows `CreateContainerConfigError`, `CreateContainerError`,
`InvalidImageName` and `ErrImageNeverPull`. ImagePullBackOff is among the most
common failures in Kubernetes; the platform currently cannot name it.

**Why no test caught it.** Every fixture feeds `status` as a single aggregated
string (`"ImagePullBackOff"`), the shape `kubectl get pods` *prints*. The real
API returns phase and waiting reason as separate fields. The fakes encode the
same misunderstanding as the code.

**Suggested fix.** Examine container statuses first and fall back to phase, so
the more specific reason always wins:

```python
def _detect_pod_status(self, pod):
    status = pod.get("status", {})
    for cs in status.get("containerStatuses", []) or []:
        state, last = cs.get("state", {}), cs.get("lastState", {})
        for reason in (
            state.get("waiting", {}).get("reason"),
            state.get("terminated", {}).get("reason"),
            last.get("terminated", {}).get("reason"),
        ):
            if reason in PROBLEM_STATUSES:
                return reason
            if reason in ("ContainerCreating", "CreateContainerConfigError",
                          "CreateContainerError", "InvalidImageName", "ErrImagePull"):
                return reason
    phase = status.get("phase")
    if phase in PROBLEM_STATUSES:
        return phase
    ...
```

Add `ErrImagePull`, `CreateContainerConfigError` and `CreateContainerError` to
`PROBLEM_STATUSES` and to `POD_STATUS_SIGNALS`. **Regression test must be built
from a real captured `kubectl get pods -o json` payload**, not a hand-written
fake — otherwise it re-encodes the same error.

### BUG-02 — `image.not_found` fires on any `Failed` event containing "not found" (HIGH)

**Component:** `backend/app/analysis/deep_signal_rules.py:253-273`

```python
if event.get("reason") not in {"Failed", "FailedPull", "ErrImagePull"}:
    continue
...
elif "not found" in lowered or "manifest unknown" in lowered or "404" in lowered:
    -> SignalType.IMAGE_NOT_FOUND, Severity.CRITICAL
```

`Failed` is heavily overloaded in Kubernetes. The kubelet emits it for config
errors, mount errors and runtime errors as well as image pulls. A missing
ConfigMap produces `reason: Failed`, `message: Error: configmap "x" not found`
— which contains the substring `not found`.

**Evidence (live):**

```
event:   reason=Failed  obj=notifier-...  msg=Error: configmap "notifier-config" not found
signal:  image.not_found  severity=critical
         "Image or tag does not exist in the registry: Error: configmap
          "notifier-config" not found"
```

**Impact.** An operator is shown a CRITICAL signal whose own text contradicts
itself, pointing at the registry when the fix is to create a ConfigMap. It also
feeds `IMAGE_NOT_FOUND` as *supporting* evidence to the image hypothesis and
into `remediation/rules.py:372`, which is built to emit "correct the image
reference". This is worse than a miss: it is a confident wrong answer, and it
directly undercuts the product's central promise that nothing is asserted
without evidence.

**Suggested fix.** `Failed` alone is not an image event. Require image-specific
phrasing before classifying:

```python
IMAGE_PULL_PHRASES = ("failed to pull", "pull access denied", "manifest unknown",
                      "manifest unknown to registry", "not found: manifest",
                      "failed to resolve reference", "errimagepull")
if reason == "Failed" and not any(p in lowered for p in IMAGE_PULL_PHRASES):
    continue
```

and add a case asserting that a missing-ConfigMap event produces **no** image
signal.

### BUG-03 — A Running-but-never-Ready pod is invisible to `problematic_pods` (MEDIUM)

**Component:** `backend/app/kubernetes/pod_inspector.py:_detect_pod_status`

`gateway` has a readiness probe pointed at a closed port. It is `phase: Running`
with `ready: false`, permanently. `_detect_pod_status` consults phase,
container waiting/terminated reasons and `PodScheduled` — but never `ready` or
the `Ready` condition — so it returns `None` and the pod is omitted entirely.

**Evidence:** `gateway-6868567865-sdccp` appears in neither run's
`problematic_pods`, while `kubectl` reports `Running / ready=False` and the
Service in front of it has zero endpoints.

**Impact.** Detected in this pass only through the `Unhealthy` event. Kubernetes
events default to a 1-hour TTL, after which a permanently broken pod looks
healthy in the pods section. "Running but never Ready" is one of the most common
production failure shapes and is precisely what a no-endpoints incident is made
of — the platform found the *symptom* (`network.no_endpoints`) but not the pod
causing it.

**Suggested fix.** Treat `phase == "Running"` with a `Ready` condition false for
longer than a short grace period as problematic, with a distinct status such as
`NotReady`, and map it to a `pod.not_ready` signal.

### BUG-04 — No length validation on request inputs (MEDIUM)

**Component:** `backend/app/api/investigations.py` request models

A 1 MB `context` string was accepted and returned 202. The value is persisted
into the job row's `request` jsonb **and** into the append-only audit log. An
authenticated caller can inflate both stores without limit; the audit log in
particular is designed never to be pruned.

**Suggested fix.** `max_length` on `context`, `namespace`, `resource_name` and
`resource_kind` in the Pydantic models — Kubernetes names are bounded at 253
characters, so a generous 512 is still two orders of magnitude tighter than
today. Truncate on the audit-log path independently, since it must remain
bounded regardless of what the API accepts.

### BUG-05 — PDF corrupts every non-ASCII character (HIGH)

**Component:** `backend/app/services/history_service.py:_pdf_bytes` (~line 877)

The three base-14 font dictionaries are emitted with no `/Encoding` entry:

```
/Type /Font /Subtype /Type1 /BaseFont /Helvetica
/Type /Font /Subtype /Type1 /BaseFont /Helvetica-Bold
/Type /Font /Subtype /Type1 /BaseFont /Courier
```

Verified on the live 36 KB report: **zero occurrences of `Encoding` in the
entire document.** Text is then written with `pdf.encode("latin-1",
errors="replace")`. Absent an explicit encoding, a Type1 base-14 font uses
**StandardEncoding**, in which the latin-1 byte 0xE9 (`é`) is not `é` — it maps
to `Ø`. So `Café naïve` renders as mojibake, and any CJK or emoji character
becomes `?`.

**Impact.** The PDF is the artefact most likely to be attached to a customer's
incident record. Any non-English namespace, container name, node label or log
line renders wrongly — silently, with no error anywhere. This also contradicts
`CLAUDE.md`, which states text is "pre-wrapped and non-ASCII escaped"; the
escaping covers a handful of typographic characters only.

**Suggested fix.** One token per font dictionary:

```
/Type /Font /Subtype /Type1 /BaseFont /Helvetica /Encoding /WinAnsiEncoding
```

WinAnsiEncoding agrees with latin-1 across the printable range, which makes the
existing encode call correct rather than incidental. Characters outside latin-1
still need transliteration — that limit should be stated in the docstring rather
than left implicit. Test by asserting a round-tripped `é` survives extraction.

### OBS-01 — Root cause need not be the highest-confidence hypothesis (observation, not a bug)

`hypothesis_rules.rank()` sorts by `(severity, confidence, breadth, id)`. In run 1
this selected a **CRITICAL at 90%** over a **HIGH at 92%**. That is deliberate
and defensible — a critical finding should outrank a marginally more likely
lesser one — but nothing in the output explains it. A reader sees a 92%
hypothesis listed and a 90% one chosen, and has no way to know severity was the
tiebreak. Surfacing the ordering rationale in the diagnosis would remove an
avoidable credibility hit.

## 7. Reliability Findings

- **Graceful degradation is real.** With no API key the LLM call failed cleanly,
  `diagnoses_total{path="fallback"}` incremented, and the investigation still
  produced a complete diagnosis with confidence and remediation. This is the
  single most valuable reliability property in the system and it works.
- **Partial collection degraded correctly.** 2 `unavailable` and 1 `failed`
  record reduced completeness to 93% without failing the job — the
  partial-versus-total distinction behaved as designed.
- **Timing sensitivity in detection.** Run 1 recorded `checkout` as `Error`;
  run 2, ninety seconds later, recorded `CrashLoopBackOff`. Both are defensible
  readings of a flapping pod, but it means **the diagnosis for the same cluster
  changed between runs**, and the root cause changed with it. Worth an explicit
  decision: prefer the steady-state reason (`lastState` plus restart count) over
  the instantaneous one, so repeated investigations of an unchanged cluster agree.
- Not exercised this pass: worker death and lease reaping, Redis loss, Postgres
  loss, cancellation under load. All have tests; none were re-verified live.

### The one thing to take away

Every automated gate in this repository was green while the platform failed to
diagnose an ImagePullBackOff sitting directly in front of it. The defect was not
subtle and not deep — it was one `if` in the wrong order — and it survived
because the fixtures feeding it were written from the same misunderstanding as
the code. The repository already knows this lesson; `CLAUDE.md` records seven
defects found by running the app rather than testing it, and the null-contexts
500 that 1,167 passing tests missed.

This audit is the eighth instance. The corrective action is not more tests. It
is **fixtures captured from real clusters**, for the pod inspector first and
then for every inspector that parses API-server output.

All six Tier-1 items are closed. Five were code changes; one was withdrawn

| 3 | BUG-05 — PDF encoding | **Fixed.** All three font dictionaries declare `/Encoding /WinAnsiEncoding`. |
| 4 | Real fixtures | **Done.** `tests/fixtures/real_pods_kind_qa.json` — 10 pods captured verbatim from the audit cluster. |
| 5 | `AUTH_MODE` default | **Withdrawn — the finding was wrong.** See below. |
| 6 | BUG-04 — unbounded inputs | **Fixed.** `max_length=512` on all four `InvestigationRequest` fields. |

### Verified against the same live cluster

Re-running the identical investigation after the fixes:

```
                          before                after
ledger                    "Pending"             "ImagePullBackOff"
pod.image_pull_failure    -- NOT FIRED --       ledger-5474c5c9bf-gtp9c
image.not_found           notifier (wrong)      -- none --
image.pull_failure        (no such hypothesis)  90% CRITICAL
signals                   36                    43
PDF fonts with /Encoding  0 of 3                3 of 3
```

The image hypothesis did not exist in any earlier run. It is not a
reordering — it is a diagnosis the platform was structurally incapable of
reaching.

### Item 5 was wrong, and how

The audit reported "insecure by default" as HIGH on the strength of
`auth_mode: str = Field(default="disabled", ...)`. That is a true statement
about the default *value* and a false one about the behaviour. Checked
empirically rather than read:

```
Settings(_env_file=None).validate_auth()
  -> ValueError: AUTH_MODE=disabled leaves every endpoint unauthenticated ...
     Set ALLOW_INSECURE_NO_AUTH=true to acknowledge this for local development,
     or configure AUTH_MODE=oidc or AUTH_MODE=token.

AUTH_MODE=token, no API_TOKENS
  -> ValueError: AUTH_MODE=token requires API_TOKENS to define at least one token
```

Both paths refuse. A fresh install cannot serve a single request until an
operator chooses, and the insecure mode requires asking for it by name. Making
`token` the default would therefore have bought no security while breaking
every local-development deployment that relies on the acknowledgement — a
change with only a cost.

What survives is that `default="disabled"` in `config.py` *reads* as an
insecure default to anyone who does not also read `build_authenticator` — which
is how this error was made. The durable fix for that is a test that states the
behaviour where someone looking at auth will find it, so
`TestTheShippedDefaultCannotServeUnauthenticated` pins the refusal, the wording
that names the secure alternatives, and the acknowledgement that still permits
local development.

**The lesson is the one this audit already argued in the other direction:**
a control that is present, correct and *inert* is a real risk — and so is one
that is present, correct and mistaken for absent. Both are found by running the
thing, not by reading it.

### Every new invariant was mutation-tested

A test that passes against the broken version is not a control. Each fix was
reverted in turn and the suite re-run:

```
CAUGHT    BUG-01  phase checked before container reason
CAUGHT    BUG-01  ErrImagePull dropped from the recognised reasons
CAUGHT    BUG-02  image-event gate removed
CAUGHT    BUG-02  gate accepts any Failed event
CAUGHT    BUG-05  encoding removed from one font only
CAUGHT    BUG-04  bound removed from one field only
```

Two results are worth keeping:

- **The pre-existing 43 inspector tests all passed with BUG-01 reinstated.**
  That is the audit's central claim, demonstrated rather than argued: those
  fixtures cannot distinguish the broken implementation from the fixed one.
- **`ErrImagePull` survived the first sweep.** The fixture had captured
  `ledger` only after it settled into `ImagePullBackOff`, so the transient
  reason was untested. Fixed by capturing a pod *mid-pull* from the same
  cluster — a hand-written case would have re-introduced exactly the problem
  this file exists to prevent.

### Not fixed here (Tier 2 and below)

Deliberately out of scope, and visible in the same live run: `notifier` still
reports `Pending` rather than `CreateContainerConfigError`, because adding new
container reasons requires new signal types and hypothesis wiring (§10 items
8-9). `gateway` is still absent from `problematic_pods` (BUG-03, item 7). The
remaining 44 improvements stand as written.
